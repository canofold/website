# 为什么选择 Canofold

写文档已经需要投入时间，发布和复用不该再变成另一份工作。Canofold 的选择很明确：知识留在仓库，页面尽量静态，同一份内容也能直接交给 AI。

## 知识归你，工作流也归你

文档和代码一起评审，或放在独立的知识仓库里。修改有 diff，发布有提交记录，历史可以回溯。团队继续使用熟悉的 Git、分支和 CI，不必为了维护文档引入另一套内容后台。

接入时，`canofold init` 补齐缺少的配置与文件，已有内容留在原处。产物可以部署到自己的静态托管平台；私有知识库则由 Access 或内部网关保护整个输出目录。内容的所有权和交付方式都由团队决定。

## 让静态内容保持轻量

读一篇文档，应该先拿到正文。Canofold 在构建时生成完整 HTML，Tabs、代码复制等交互使用原生 DOM 增强，无需对整页内容做 React 水合。

需要执行组件的地方才运行组件：React Demo 通过 Vite 接入，图表按插件加载。这样既能写带交互的技术文档，也能把普通内容的运行时成本控制住。

生产部署只需静态文件服务。团队维护的是内容与构建流程，而不是一台专门运行文档应用的服务器。

## 给人读，也给 AI 用

把网站搭好之后，再写抓取和清洗脚本给 AI 使用，往往会重复处理标题、正文与来源。Canofold 在构建阶段就能输出 Markdown 镜像、`llms.txt`、页面元数据和 JSONL 分片。

这些输出与页面一起更新，并保留可引用的来源。你可以把它们接入自己的 Agent、检索系统或向量库；模型与检索服务由你选择。Canofold 负责把知识准备好。

[Skills](/skills/)进一步把这种工作方式带到 Agent：依据项目写内容、根据代码同步说明、从指定语言与版本的文档中查找答案。这部分仍在实验中，可以从一个具体任务试用。

## 哪些项目值得试

如果你在维护开源项目、React 组件库，或用 Git 管理团队知识，希望文档既有完整的阅读体验，又能服务搜索和 AI，Canofold 值得用几篇真实内容试一次。14 套主题、实时 Demo 和 VS Code 预览可以直接加入这条工作流。

如果核心需求是浏览器内多人协作、逐页权限或审批评论，在线 CMS 或协作知识库通常更合适。Canofold 选择静态发布模型；多语言译文与历史快照由团队维护，工具负责组织路由、切换与检查。

MDX、本地组件和构建扩展会执行代码，适合可信仓库内容。处理外部输入前请先阅读[安全边界](/reference/output/security/)。

## 用三步判断是否合适

1. [安装并初始化](/guide/introduction/getting-started/)，放入三到五篇已有文档，保留其中真实的链接、图片与代码示例。
2. 运行 `canofold check` 和 `canofold build`，检查导航、搜索与所需的 AI 输出是否符合预期。
3. 用 `canofold preview` 阅读构建结果，在 VS Code 中修改一篇内容，再决定是否接入更多文档。

先验证自己的写作与阅读场景，再扩展主题、插件和多语言配置。
